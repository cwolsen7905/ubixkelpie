# Kelpie's database

The MariaDB database `ubixkelpie`, one per tier, with migrations run by CI. Set up 2026-10-17.
Passwords never go in this repo, an MR or a chat; they live in uBixVault only.

## 1. Where things are

| Tier | Branch | Server | Vault (CI and pods) | Namespace |
|---|---|---|---|---|
| dev | `dev` | `10.50.25.62:3306` | vault.dev | `kelpie-dev` |
| staging | `staging` | `10.50.25.61:3306` | vault.dev | `kelpie-staging` |
| prod | `main` | `10.50.25.45:3306` | vault.prod | `kelpie-prod` |

**The Vault rule:** vault.prod holds production only; dev and staging both use vault.dev. A leaked
dev token or a policy mistake on the dev Vault must never reach a production secret. Staging may
sit with dev because it has its own server and accounts; it must never get a production
credential.

## 2. Accounts

Two per server, created by a DB admin (section 5). The host part is `%` on all three.

| Account | Used by | On `ubixkelpie.*` | On `SYSTEMS` |
|---|---|---|---|
| `ubixkelpie` (app) | pods; `write_username` | `SELECT, INSERT, UPDATE, DELETE` | `SELECT, UPDATE (sanitised_at, sanitised_by)` on `Database_Environment` |
| `ubixkelpie_ddl` (migrations) | CI migrate jobs only; `migration_username` | `SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES` | `SELECT, INSERT, UPDATE, DELETE` on `Schema_Migrations`; `SELECT, INSERT, UPDATE, CREATE` on `Database_Environment`; both `WITH GRANT OPTION` |

Why `SYSTEMS`: uBixCore records applied migrations for every project on the server in
`SYSTEMS.Schema_Migrations`, and the server's declared environment in
`SYSTEMS.Database_Environment` (it runs `CREATE TABLE IF NOT EXISTS` on that table, hence
`CREATE`). The grants are table-level on purpose: `SYSTEMS` is shared, and other projects keep
tables there (kitg's PII audit trail), which neither Kelpie account can see. MariaDB cannot limit
a grant to Kelpie's own rows, so the DDL account could still change other projects' tracker rows;
that is the one remaining shared risk, the same as every app's.

The DDL password exists only in CI's secret; pods never hold it.

## 3. Vault secrets

| Path (under `secret/`) | Vault | Read by | Keys |
|---|---|---|---|
| `kelpie/db-<tier>` | as in section 1 | CI migrate jobs | `host`, `port`, `database` (`ubixkelpie`), `write_username`, `write_password`, `migration_username`, `migration_password` |
| `kelpie/<tier>/db` | as in section 1 | pods (`VAULT_DB_KV_PATH`) | `read_username`, `read_password`, `write_username`, `write_password` (all the app account) |
| `kelpie/test-db` | vault.dev and vault.prod | CI `phpunit-<tier>` | `host`, `port`, `username`, `password`, `database` (the shared `ubixcore-test-db` account on each runner) |

CI reads with `UBIXVAULT_CI_TOKEN_DEV` / `UBIXVAULT_CI_TOKEN_PROD` (GitLab variables, protected,
masked; policy `kelpie-ci-ro`: read `secret/kelpie/*`). Pods log in with the k8s role
`kelpie-<tier>`, whose policy `kelpie-<tier>-ro` reads `kelpie/<tier>/*`, on that tier's Vault.

To change one key, use uBixCore's `vendor/ubixsys/ubixcore/ci/bin/vault-set-key.sh` (value at a
prompt or piped from a file, never in argv; lower-case keys need `--any-case`).

## 4. How CI uses it

The pipeline is uBixCore's template (`.gitlab-ci.yml`). Per tier:

- `migrate-verify-<tier>`, then `migrate-apply-<tier>`: reads `kelpie/db-<tier>`, refuses to run
  unless its `host` equals `MYSQL_WRITE_HOST` in `app/KelpieApi/<branch>-deploy.yaml`, runs
  `migrate:status` and `migrate:up` as the DDL account, then applies `sql/grants/app.sql`.
  On staging and prod a `Destructive:` migration holds until someone runs the `-destructive` job.
- `migrate-apply-prod` is manual: it is the production release click; `deploy-prod` follows it.
- `phpunit-<tier>` rebuilds `ubixkelpie` on the runner's test database and runs every migration
  before the suite, so a broken migration fails there first. `phpunit-mr` runs the suite only
  (MR pipelines cannot read the protected Vault tokens).

## 5. Setting up a server again

As a DB admin, with the passwords generated by you and written straight to Vault (section 3):

```sql
CREATE DATABASE IF NOT EXISTS ubixkelpie CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

CREATE USER IF NOT EXISTS 'ubixkelpie'@'%' IDENTIFIED BY '<app-password>';
GRANT SELECT, INSERT, UPDATE, DELETE ON ubixkelpie.* TO 'ubixkelpie'@'%';
GRANT SELECT, UPDATE (sanitised_at, sanitised_by) ON SYSTEMS.Database_Environment TO 'ubixkelpie'@'%';

CREATE USER IF NOT EXISTS 'ubixkelpie_ddl'@'%' IDENTIFIED BY '<ddl-password>';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES
    ON ubixkelpie.* TO 'ubixkelpie_ddl'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON SYSTEMS.Schema_Migrations TO 'ubixkelpie_ddl'@'%' WITH GRANT OPTION;
GRANT SELECT, INSERT, UPDATE, CREATE ON SYSTEMS.Database_Environment TO 'ubixkelpie_ddl'@'%' WITH GRANT OPTION;
```

The `SYSTEMS` tables must exist first (another app's migrations, or uBixCore's bootstrap,
create them); a table-level `GRANT` on a missing table fails.

## 6. Checking it

1. The tier's `migrate-apply-<tier>` log shows `host cross-check OK`, the migration list and
   `App grants applied (sql/grants/app.sql).`
2. `SELECT * FROM SYSTEMS.Schema_Migrations WHERE target_database = 'ubixkelpie';` lists
   `20261015120000_create_autofix_jobs`, and `SHOW TABLES FROM ubixkelpie;` shows `autofix_jobs`.
3. `SHOW GRANTS FOR 'ubixkelpie'@'%';` lists exactly the app row of section 2, nothing wider.
4. The pod is ready after the deploy (the rollout wait fails the deploy if Vault or the database
   credentials are wrong). `/health` does not touch the database yet.
